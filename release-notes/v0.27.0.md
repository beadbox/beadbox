## What's New in v0.27.0

### Breaking change: beads 1.1.0 or newer is required

Beadbox now requires beads 1.1.0 or newer. Older versions see an upgrade prompt at startup. Upgrade with `brew upgrade beads` on macOS, or per the [beads README](https://github.com/gastownhall/beads#readme) on other platforms.

### Security

- **Formulas and molecules: stricter handling of names.** Formula, formula variable and molecule names are now validated before they are passed to `bd`, closing a way for a crafted name to change which workspace an operation applied to. Dependency and label operations received the same hardening.

### Fixed: adding a shared Dolt server as a workspace could lock other clients out

**Who is affected.** Anyone who used **Add workspace → Advanced** in Beadbox 0.25.1–0.26.2 to add a Dolt server that other clients also use. What happened depends on the beads version on the Beadbox machine *when the workspace was added*, not the version installed now:

- With beads **1.1.x** or **1.2.2** on that machine, adding the workspace replaced the server's project id with a new one. Every *other* client of that server then failed with `PROJECT IDENTITY MISMATCH — refusing to connect`. The server's data is untouched; only its identity changed.
- With beads **1.2.1** or **1.3.0**, usually only Beadbox itself failed to open the workspace and other clients were unaffected — but check the symptom below rather than assuming.
- If the beads version on the Beadbox machine differed from the server's, the add failed outright and nothing was written.

In 0.27.0 the workspace adopts the server's own identity instead, and a workspace damaged by an earlier version is shown as **"Workspace needs to reconnect"** rather than a generic error.

**How to tell which case you have.** If `bd list` in another client of that server prints `PROJECT IDENTITY MISMATCH`, you have the first case: do all three steps. If only Beadbox shows "Workspace needs to reconnect", skip to step 3.

**Repair**

1. Update Beadbox to 0.27.0 on the machine that added the server workspace.
2. *(First case only)* Put the server's project id back to the one your other clients print as "Local project ID (metadata.json)" — it is also the `project_id` in their `.beads/metadata.json`. Either way works:
   - From the Beadbox machine, inside the workspace's own scaffold (the one that still matches the server):
     ```sh
     grep -l '"dolt_database": "<database name>"' ~/.beadbox/workspaces/*/.beads/metadata.json
     cd ~/.beadbox/workspaces/<the id from that path>
     BEADS_DOLT_AUTO_START=0 bd sql "UPDATE metadata SET value='<original id>' WHERE \`key\`='_project_id'"
     ```
     Expect `OK, 1 rows affected`. Add `BEADS_DOLT_PASSWORD=<password>` in front if your server needs one.
   - Or from any MySQL client connected to the server's database as a user who can write it:
     ```sql
     UPDATE metadata SET value = '<original id>' WHERE `key` = '_project_id';
     ```
   Then check: `bd list` in one of your other clients works again.
3. In Beadbox, open the workspace. It shows **"Workspace needs to reconnect"** — click **Remove workspace**, then add the same server again. (If you see the error in the tree instead, open the workspace's **⋮** menu in the sidebar, choose **Remove**, and add the server again.) Beadbox now connects using the server's own project id. The old scaffold folder under `~/.beadbox/workspaces/` is left in place and can be deleted.

Do not run `bd init` in your other clients to "fix" the mismatch — that mints yet another identity. A project folder (not a server added in Beadbox) that shows the same message should run `bd doctor` there instead.

Requires the [beads](https://github.com/gastownhall/beads) CLI, version 1.1.0 or newer.
